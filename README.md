# SnapEyes

Iris art from a phone photo. Marketing page at `/` (React + Vite + Tailwind) and the real studio at `/try`.

## How `/try` works

1. **Capture** (`src/try/TryApp.tsx`): the phone's own camera via `<input capture>`, or a gallery pick of 3-5 shots. There is no in-page live camera: a browser camera stream gives much softer photos than the camera app (no multi-frame processing, no telephoto switch, poor close focus). The photo never leaves the browser at full size: a 1600 px copy goes to analysis, then only the iris square (max 1400 px) is sent on.
2. **`POST /api/analyze`**: Gemini vision returns iris/pupil/glare boxes as JSON, a Daugman-style limbus fit refines the circle, size and sharpness are measured. Verdict: `good` (iris >= 500 px and sharp), `ok`, `weak`, with concrete tips.
3. **`POST /api/deglare`**: disk mask, Real-ESRGAN x4 (ONNX, CPU) when the iris is small, glare mask (relative brightness + vision boxes), and a Gemini image edit that rebuilds only the reflection area, blended back through a feathered mask.
4. **`POST /api/enhance`**: `faithful` = conservative restoration prompt with `thinking_level: high` plus a fidelity guard (low-frequency SSIM against the input; below 0.75 falls back to the faithful upscale). `artistic` = macro re-interpretation for weak photos. With consent the crop, result and metrics are stored to Vercel Blob (`eyes/<session>/…`) as training memory. The page never gets the clean result (`api/_lib/preview.py`): `image` is an 800 px display copy with the preview watermark across the iris, `sealed` the clean 1024 px JPEG encrypted and authenticated with a server-only key (HMAC-SHA256 keystream and tag, 48 h expiry), `sealed_sizes` the same at 768 and 560 px for 3-8 eyes. The order draft (`api/order.py`) opens `sealed` and stores the clean bytes, so `/api/master_eye` gets exactly the enhance output as its preview.
5. **`POST /api/compose`**: takes the sealed irises (opened on the server), PIL composition on the style backgrounds in `api/_assets/bg` with Cinzel/Plus Jakarta typography and a preview watermark, returned at 1024 px. The watermark's words are drawn at the display copy's strength on every iris disc (`iris.WATERMARK_IRIS`), so the artwork and its "Save preview" file carry no clean iris either. Only `sealed` (the clean 1024 px original) opens into an order's preview; the smaller `sealed_sizes` copies open only here.

`GET /api/health` reports what is configured on a deployment.

## Languages and markets

The site speaks English, German, Lithuanian and Hungarian. The language and the market are two separate things, both taken from the link and neither moving the other: `?lang=` picks the language, `?m=` the market (`eu`, `lt`, `hu`, `au`; currency and prices in `api/_lib/markets.py`). Nothing redirects. A page's language is, in this order: `?lang=`, the visitor's earlier choice (localStorage `snapeyes.lang`), the market's own language (`lt` Lithuanian, `hu` Hungarian, set in `markets.py`), the browser's language, English (`src/shared/lang.ts`). The Australian market is English and German only, because the Australian legal texts are.

- The words: `src/landing/copy*.ts`, `src/try/copy*.ts`, `src/order/copy*.ts` (English and German in the main file, `*.lt.ts` and `*.hu.ts` beside it, typed by the English dictionary: a missing key fails `tsc`). The legal texts are `src/legal/docs/*.ts` with `*.lt.ts` and `*.hu.ts`; the editions (EU, Australian, Hungarian with the forint prices) are `src/legal/editions.ts`, and which languages an edition has is `EDITION_LANGS` in `src/shared/legal.ts` and `api/_lib/pay.py`.
- The server: `api/analyze.py` (`TEXT_DE`, `TEXT_LT` in `api/_lib/analyze_lt.py`, `TEXT_HU` in `analyze_hu.py`), `api/_lib/iris.py` (error sentences, `WATERMARK_TEXT`), `api/_lib/pay.py` and `withdraw.py` (emails and receipts, with the Lithuanian and Hungarian texts in `pay_lt.py`, `pay_hu.py`, `withdraw_lt.py`, `withdraw_hu.py`). The order confirmation email carries the legal texts of the order's edition and language from `/legal/order-mail.json`, which the build writes.
- `npm run check:texts` (it also runs before every build) refuses: a Lithuanian or Hungarian dictionary with other keys than the English one, an untranslated English sentence, a dash, a missing sentence for a photo block reason, a legal text missing in a language of its edition, terms that print another currency's prices or do not name every contract language, a consent version in the future or different from the server's, and a withdrawal waiver or statement that is not the same words on the page and on the server. A new function in a copy dictionary needs sample arguments in `scripts/check_texts.mjs`. Hungary is sellable (`"selectable": 1`) only together with its legal edition; `npm run check:prices` enforces that.
- Adding a language means: its dictionaries, its legal texts, `LANGS` in `src/shared/lang.ts` and `api/_lib/pay.py`, its words in the terms' contract-languages sentence in every language, `hreflang` in the five indexable pages and `public/sitemap.xml`, its watermark (measured on every canvas), its analyze sentences, its emails and a new consent version.
- `npm run check:texts` also keeps the two lists honest that nobody reads by hand: a Lithuanian or Hungarian string that is word for word the English or German one, English or German function words in any Lithuanian or Hungarian string (the dictionaries, the legal texts, the built legal pack and the customer sentences in `api/_lib/*_lt.py` and `*_hu.py`), and a consent text that changed under the same consent version (`CONSENT_FINGERPRINTS` in `scripts/check_texts.mjs`: changing a consent text needs a new `CONSENT_VERSION` in `api/_lib/pay.py` and `WITHDRAWAL_CONSENT_VERSION` in `src/shared/legal.ts` together, and the new fingerprint, which the check prints). A word that is also a real Lithuanian or Hungarian word stays off its lists on purpose (`WORDS_EN`, `WORDS_DE`); a word that has to stay English goes into `ENGLISH_OK`.
- Before Lithuanian and Hungarian sales start (nothing here has been read by a lawyer):
  - The one switch for every language and market is ordering itself (the live Stripe keys; `ordering_problem()` in `api/_lib/pay.py`). `"selectable": 0` for `hu` in `api/_lib/markets.py` only hides the forint market. It does NOT stop Hungarian: `?lang=hu` (or a Hungarian browser) on the euro market still shows the Hungarian pages and accepts an order under the Hungarian terms, and Lithuanian has no switch at all. There is no cheap per-language switch: the terms of every edition name their contract languages, and the text check demands that the Hungarian texts and those sentences leave together. So keep the live Stripe keys off until the Hungarian texts have been read by a Hungarian lawyer, or do not deploy this release until they have.
  - Hungarian: the legal texts were written from 45/2014. (II. 26.) Korm. rendelet and 373/2021. (VI. 30.) Korm. rendelet. For the lawyer: the buy button label (`CHECKOUT_LEGAL.hu.continueButton`, 15. § (2)), where the order binds (Stripe's pay button, whose note carries the decree's words), the out-of-court body to name. The owner confirms or deletes the promise to answer every complaint within 30 days (terms, `disputes`). Ask the accountant about VAT (every "no VAT" sentence rests on the EU distance-sales threshold) before the first Hungarian sale.
  - Lithuanian: the withdrawal page quotes the model of order 1R-154 with the online-function sentence of Directive (EU) 2023/2673, so check e-tar.lt for an amended 1R-154 (`src/legal/docs/withdrawal.lt.ts`, section `right`). The English and German terms already name Lithuanian and Hungarian as contract languages, so the texts of this release go out together.
  - Not read by a native speaker: besides the two packs, the lines the integrator wrote (the `eyelid` and `too_small` blocks and sentences, the Hungarian `result.previewFile`/`previewReduced` lines, the market hint and currency footnotes, the forint and euro price paragraphs of the terms, the privacy storage and country-hint paragraphs, the contract-languages sentences, the Lithuanian Stripe sentence about the obligation to pay). Give them to the readers with the packs' own review tables.
  - Withdrawal periods now also run past 15 Mar, 20 Aug and 23 Oct for every order, English, German and Australian ones too (`HOLIDAYS_HU` is in the one holiday table, the latest end anywhere is taken): one working day longer on those days, on the consumer's side. `LEGAL_UPDATED` stays 2026-09-30, the day the previous texts went live: keep the deploy time of this release in your notes.

## Price experiments

Price tests are defined in one place, `api/_lib/experiments.py` (every variant carries its FULL ladder per market; the variant `control` is the standard ladder of `api/_lib/markets.py`; a finished test is kept with `"retired": 1`). Nothing runs until the owner starts it in the admin page "Kainų testai" (`/admin#tests`); the state is `ops/experiments/<key>.json` in the private bucket and every start and stop is in the admin audit log (with the risks the owner accepted). Off, the site behaves exactly as before, and the browser keeps nothing.

- The page asks `GET /api/checkout` without any id, as it always did. Only while a test runs does the answer also name the markets that run one (`exp_markets`). A visitor of such a market (who has not opted out with `?pricetest=off`, the link in the privacy policy) gets a random anonymous id in localStorage (`snapeyes.vid`, 90 days at most, deleted again when no test runs) and asks once more with the id in the header `X-Snapeyes-Visitor` (never in a URL). The server derives the variant from the id (sticky), answers with that variant's ladders and a signed assignment token (HMAC under the ticket secret). `POST /api/checkout` prices the order from the verified token only (`api/_lib/abtest.py`); no valid token means the standard ladder, and a page that sends the price it showed (`shown`) gets `409 price_changed` instead of a different charge.
- The experiment, variant and ladder are recorded in `order.json` (checkout.experiment), the Stripe metadata (`exp`, `exp_var`, `exp_lad`) and `paid.json` (experiment with the ladder that applied); `session_matches` refuses a paid session whose amount is not the price of its own ladder, and the confirmation email names the price list that applied. Because the ladder travels with the session, editing, retiring or deleting a test never makes an open checkout unpayable. Rule of thumb: stop the test, wait 24 hours, then change prices or definitions.
- Anonymous events (kind `exp`: visit, preview, checkout, paid) give the visitors, previews and payment pages per variant; paid orders and revenue come from the order records (live payments, refunded and withdrawn ones apart). The admin page shows the funnel, conversion, revenue per visitor and average order in the test's currency, significance tests (conversion, the affected orders, revenue per visitor; a p-value only with at least 10 paid orders and 100 visitors per arm, and a verdict only once the planned size is reached), the sample size needed, orders that took no part, and a warning when a ladder would sell at a loss (`COSTS` in the same file).
- `npm run check:prices` (and every build) validates every variant ladder (`scripts/check_experiments.mjs`) and that the page's price rule agrees with the server's. Never edit a ladder that has run: add a new experiment key instead.

## Styles

Which styles exist is defined in one place, `api/_lib/styles_registry.py`: the ids, brand names, slugs, eye counts, layouts, the stage ceiling, the price class (`black` or `art`), the gate policy and the sizes a render may work at. How each style is drawn is in `api/_lib/styles_engine.py`, which only Python reads (the public file is imported by the pages as text and ships in their JavaScript). The server asks `api/_lib/catalogue.py` (`known`, `orderable`, `previewable`, `stage_of`, `price_class`, `engine_for`, `tiles_for`, `pick_for`, ...), the pages ask `src/shared/styles.ts`; nobody else keeps a list of style ids, a style name or the rule that makes a style cost the black price.

- The stage in the file is the CEILING (`planned`, `lab`, `preview`, `live`, `retired`); the owner's override in the admin page can only lower it. The six ids of today carry `legacy: 1` and stay `live` until the v3 cutover. The v3 ids are `lab` or `planned`, so no customer can preview or order one, and a style whose engine module is not in the repository is never routed to, whatever its stage says (`catalogue.engine_built`).
- `npm run check:styles` (and every build) refuses a registry that breaks the schema, two ids with one slug, a heart or a pet symbol in an id, a style id written in any other file of `api/`, `src/` or `scripts/` (the allow list is in `scripts/check_styles.mjs`), a copy dictionary keyed by style id that does not match, a layout without a name, and price rules that disagree; it prints the registry hash (12 hex digits, also `catalogue.registry_hash()`). The rules that need the new texts (no number of styles or of eyes in a string, the run-time tokens of the pricing rows) are built and switched off until `WP12_RULES` is set.
- A new style is a registry entry first: add it to both files, run `npm run check:styles`, and raise its stage only in a reviewed change.

## Environment variables (Vercel)

- `GEMINI_API_KEY` (required)
- `BLOB_READ_WRITE_TOKEN` (optional, enables the training memory)
- `SNAPEYES_VISION_MODEL` / `SNAPEYES_IMAGE_MODEL` (optional overrides; defaults `gemini-3.8-flash` / `gemini-3.1-flash-image`)

## Local development

```bash
npm install
python scripts/dev_api.py          # Python stand-in for the Vercel functions on :5050 (reads C:\kuriam\.gemini-key locally)
npx vite --port 5175               # frontend, proxies /api to :5050
python scripts/test_flow.py photo.jpg [--artistic]   # end-to-end API test, writes ./flowtest next to the photo
npm run build                      # tsc + vite build (both pages)
```

Python deps for local runs: `pip install -r requirements.txt`.
